# Правила работы с git

## Жёсткие правила (НЕ НАРУШАТЬ)

### 1. Коммит — только после явного разрешения
- Никогда не делай `git commit` без вопроса пользователю
- Форма вопроса: «Commit эти изменения? \n[статистика изменений]»
- Жди ответа «да», «yes», «ok» или «commit»

### 2. Push — только после явного разрешения
- Никогда не делай `git push` без вопроса пользователю
- Форма вопроса: «Push на origin/main?»
- Push только после того как коммит уже сделан
- Жди ответа «да», «yes», «ok» или «push»

### 3. Всегда показывай что будешь коммитить
Перед вопросом о коммите выполни:
```bash
git status
git diff --stat
git diff
```
Пользователь должен видеть **все изменения** перед тем как разрешить коммит.

### 4. Коммит-сообщение — осмысленное
Формат: `тип: краткое описание`
- `feat:` — новая функциональность
- `fix:` — исправление бага
- `refactor:` — рефакторинг без изменения поведения
- `ui:` — изменения интерфейса
- `docs:` — документация
- `chore:` — служебные изменения (gitignore, deps)
- После двоеточия — пробел и описание на русском или английском (как удобнее пользователю)
- Описание должно давать понять что изменилось, не вдаваясь в детали

Примеры:
```
feat: add filter-graph export strategy with trim+concat
fix: PTS-STARTPRES typo in filter_graph_strategy.dart
ui: bigger centered action buttons + larger step slider
refactor: replace extract-then-concat with single ffmpeg process
```

### 5. Верификация — строго перед коммитом
Перед тем как предлагать коммит:
- `dart analyze` / `flutter analyze` / линтер — 0 errors (info-level допустимо)
- Проверка регрессий по `fixed-bugs.md`
- Тесты пройдены (если есть)
- Если проверка не прошла — исправь, потом предлагай коммит

### 6. Никогда не force-push
- `git push --force` запрещён без явного обсуждения с пользователем
- Если нужно переписать историю — спроси отдельно

### 7. Не коммить пустые изменения
- Если `git status` показывает «nothing to commit, working tree clean» — не предлагай коммит
- Если изменений нет — скажи «Изменений нет, коммитить нечего»

## Типовой диалог

```
# После верификации, когда есть изменения:
> git status
> git diff --stat
> git diff

«Я проверил: analyze → 0 errors, регрессии → 0 совпадений.
Commit эти изменения?
  feat: add filter-graph export strategy

(да/нет)»

[Пользователь: «да»]

> git commit -m "feat: add filter-graph export strategy"

«Коммит abc1234 готов. Push на origin/main? (да/нет)»

[Пользователь: «да»]

> git push origin main

«Готово, abc1234 на origin/main.»
```

## Если пользователь сказал «нет»
- Не коммить, не пушить
- Спроси: «Что нужно изменить перед коммитом?»
- После изменений — повтори верификацию и спроси снова

## Исключения
Единственное исключение: пользователь явно сказал «Commit и push без лишних вопросов» или дал одноразовое разрешение на серию изменений. Но даже в этом случае — покажи `git status` и `git diff` перед коммитом.
